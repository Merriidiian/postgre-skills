# Схема, производительность и миграции

## Схема от инвариантов

Определи авторитетные таблицы, производные данные, единицу владения и пути чтения/записи. Выбирай типы по смыслу: `timestamptz` для момента времени, точный тип для денежных расчётов, `jsonb` для действительно гибких атрибутов с понятными запросами. Не прячь обязательные связи и ключевые ограничения в произвольный JSON.

Пример tenant-локальной связи; типы ID и имена адаптируй к проекту:

```sql
CREATE TABLE projects (
    tenant_id uuid NOT NULL,
    id uuid NOT NULL,
    name text NOT NULL,
    PRIMARY KEY (tenant_id, id)
);

CREATE TABLE tasks (
    tenant_id uuid NOT NULL,
    id uuid NOT NULL,
    project_id uuid NOT NULL,
    title text NOT NULL,
    status text NOT NULL CHECK (status IN ('open', 'done')),
    version bigint NOT NULL DEFAULT 1 CHECK (version > 0),
    PRIMARY KEY (tenant_id, id),
    FOREIGN KEY (tenant_id, project_id)
        REFERENCES projects (tenant_id, id)
);
```

Составной FK не позволяет связать задачу с проектом другого tenant. Это ограничение целостности; чтение чужих задач предотвращают права, фильтры и RLS. Для реальной схемы добавь нужную связь с таблицей tenants и определённые правила удаления.

`CHECK` по строке не подходит для ограничения «не более N открытых задач у проекта» через подсчёт других строк. Такой инвариант требует спроектированной конкурентной транзакции или согласованного счётчика. `CHECK` не заменяет `NOT NULL`: выражение с результатом NULL обычно не отклоняет строку.

## Запросы и индексы

Начни с конкретных `WHERE`, `JOIN`, сортировки и ограничения выдачи. Для запроса открытых задач проекта возможен частичный индекс:

```sql
CREATE INDEX tasks_open_by_project
    ON tasks (tenant_id, project_id, id)
    WHERE status = 'open';
```

Проверь план реального запроса, включая параметризацию и предикат RLS. Планировщик должен суметь доказать условие частичного индекса; generic plan с параметризованным статусом может его не использовать. Состав и порядок колонок выводи из нагрузки, не из универсального правила «tenant всегда первый для любых запросов».

Каждый индекс занимает место и увеличивает стоимость записи, WAL и обслуживания. PK/UNIQUE создают обеспечивающий индекс, FK не создаёт автоматически индекс на ссылающихся колонках. Нужность такого индекса оцени по JOIN, проверкам удаления/обновления родителя и нагрузке.

Для глубоких списков рассмотри keyset pagination: стабильный уникальный порядок и предикат после последнего ключа. Для сортировки по неуникальному времени включи tie-breaker ID и все элементы порядка в курсор. Сохраняй tenant и фильтры. Переход по страницам в отдельных транзакциях не гарантирует единый snapshot.

## Диагностика плана

1. Зафиксируй запрос, типичные и крайние параметры, объёмы, статистику и роль.
2. Начни с `EXPLAIN`, затем используй `EXPLAIN (ANALYZE, BUFFERS)` в подходящей среде, если требуется фактическое выполнение.
3. Сопоставь estimate/actual rows, loops, время, buffers, фильтрацию, сортировки и spill. Проверь ожидания блокировок и пула: проблема может быть вне плана.
4. Измени одну обоснованную причину и повтори сравнение при одинаковых данных и ресурсах.

`EXPLAIN ANALYZE` действительно выполняет запрос, включая запись. Не запускай его для изменяющего SQL в неизвестной или рабочей среде без разрешённого плана. `ROLLBACK` не отменяет все возможные внешние эффекты функций и не откатывает потребление sequence.

Seq Scan может быть оптимален для маленькой таблицы или большой доли строк. Не отключай его как «исправление». Используй актуальную статистику, не назначая `VACUUM FULL`, `REINDEX` и глобальные настройки первым шагом диагностики.

## Нагрузочный паспорт

Зафиксируй версию СУБД и приложения, ресурсы, объём и распределение данных, read/write mix, горячие ключи, текст запроса, пул, workers, прогрев, длительность и метод генерации входа. Измеряй throughput, p95/p99, долю ошибок и насыщение, включая ожидание соединения и чтение результата.

Закрытый цикл генератора сам снижает интенсивность при замедлении; не экстраполируй его хвосты latency на независимый открытый вход. Не усредняй процентили и не сравнивай разные профили нагрузки как эквивалентные.

Пул — средство ограничения нагрузки. Увеличение `max_connections` или пула может ухудшить ситуацию: сначала установи причину ожидания, число одновременных операций и суммарное число соединений всех реплик приложения.

## Миграции

- Учитывай одновременную работу старого и нового кода. Предпочитай расширение, совместимый rollout, backfill ограниченными порциями, валидацию и позднее удаление старого контракта.
- Выясни блокировки, длительность, объём WAL и поведение при сбое конкретной команды на целевой версии. Настрой обоснованный `lock_timeout`/`statement_timeout` для операции, а не глобально наугад.
- При добавлении подходящих CHECK/FK можно отделить `NOT VALID` от `VALIDATE CONSTRAINT`. Новые строки всё равно должны удовлетворять ограничению. Это не универсальная опция для любого вида constraint.
- `CREATE INDEX CONCURRENTLY` уменьшает блокирование записи, но имеет собственную цену и не выполняется внутри обычного transaction block. Проверь поддержку мигратором; после сбоя проверь состояние индекса.
- Не выдавай удаление данных за обратимую миграцию. Для рискованного преобразования нужны известный backup/восстановление или проверенный компенсирующий план.

Основы: РХД-1, РХД-4, РХД-6–7; дополнения по SQL и миграциям сверяются с документацией целевой версии PostgreSQL.
