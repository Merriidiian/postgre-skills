# Конкурентные транзакции и идемпотентность

## Выбор механизма

Назови инвариант и воспроизведи опасное чередование операций до выбора изоляции.

| Механизм | Когда подходит | Граница гарантии |
| --- | --- | --- |
| Условный атомарный `UPDATE` | Правило выражается изменением одной строки | Нужна обработка отсутствия результата и согласованность производного счётчика |
| Блокировка общей строки `FOR UPDATE` | Все участники правила могут сериализоваться на одном владельце | Все пути изменения должны соблюдать протокол; важен порядок блокировок |
| `WHERE version = expected` | Нужно обнаружить изменение одного объекта | Не удерживает автоматически ограничение над множеством других строк |
| `SERIALIZABLE` | Решение зависит от прочитанного множества строк/предиката | Возможны отмены и полный повтор; все влияющие пути должны соблюдать совместимый протокол |

Пример атомарного резервирования одной строки:

```sql
UPDATE inventories
SET available = available - $3,
    version = version + 1
WHERE tenant_id = $1 AND item_id = $2
  AND $3 > 0 AND available >= $3
RETURNING available, version;
```

Отсутствие строки в `RETURNING` означает, что условие не выполнилось или объект недоступен/не существует; не назначай точную бизнес-причину без нужного контракта и дополнительных проверок.

Для лимита числа открытых задач `COUNT` → `INSERT` под `READ COMMITTED` или `REPEATABLE READ` может дать write skew. Блокировка существующих задач не блокирует отсутствие будущей строки. Можно блокировать общую строку проекта, вести согласованный счётчик или использовать подходящий сериализуемый протокол.

При блокировке родителя прочитай проверяемое состояние в корректном снимке. Например, под `READ COMMITTED` отдельный запрос после получения общей блокировки получает свежий снимок. Нельзя механически перенести этот вывод на старый snapshot `REPEATABLE READ`.

## Изоляция и повтор

В PostgreSQL `READ UNCOMMITTED` фактически соответствует `READ COMMITTED`. У `READ COMMITTED` снимок меняется между операторами; `REPEATABLE READ` даёт устойчивый снимок, но допускает некоторые serialization anomalies. `SERIALIZABLE` добавляет обнаружение опасных зависимостей; он не отменяет обычные блокировки записи.

Для предусмотренных конфликтов `40001` (`serialization_failure`) и `40P01` (`deadlock_detected`):

1. Откати неудачную попытку и отбрось её вычисленные результаты.
2. Если операция допускает повтор, осталось время и попытки — выжди ограниченный backoff с jitter.
3. Открой новую транзакцию, установи контекст заново и повтори весь блок чтения, проверки и записи.
4. Проверь ошибку `COMMIT` так же внимательно, как ошибки операторов.

Не повторяй только последний INSERT, приняв решение по старому снимку. Количество попыток и максимальное время выбирай по задаче; пять попыток из практикума не являются обязательным значением.

В повторяемом блоке не должно быть необратимого внешнего действия, например отправки платежа или публикации напрямую в брокер. Данные логической команды, участвующие в отпечатке и ID событий, должны быть устойчивы по контракту попыток.

Не повторяй автоматически ошибку синтаксиса, нарушение бизнес-правила или любую `23505`. Неоднозначный сетевой сбой во время `COMMIT` отличается от подтверждённого отката: сначала используй устойчивую идемпотентность/проверку результата. Отмена context имеет приоритет над бюджетом повторов.

Держи транзакции короткими, согласуй порядок захвата нескольких блокировок, измеряй ожидания и частоту retry. Лишний сетевой вызов внутри транзакции повышает время удержания ресурсов и конфликты.

## Идемпотентная команда

Схема журнала может использовать PK `(tenant_id, key)` и хранить operation, нормализованный request hash, устойчивый ответ и время создания. Другой допустимый контракт включает operation прямо в уникальную область. Выбор должен исключать возврат результата чужой операции.

```text
BEGIN
  установить tenant
  INSERT ключ команды ... ON CONFLICT DO NOTHING
  если ключ уже занят:
    прочитать запись, сравнить operation и request hash
    вернуть сохранённую квитанцию либо конфликт
  иначе:
    выполнить бизнес-изменение
    записать Outbox, если событие входит в контракт
    сохранить квитанцию
COMMIT
```

Параллельный дубликат может ждать решения первой транзакции. Не считай отсутствие вставленной строки гарантией, что конфликтующая запись видна в том же SQL-операторе: учти снимок и выбранный уровень изоляции, отдельное чтение/повтор. При `SERIALIZABLE` ожидай полный retry по соответствующему SQLSTATE.

Квитанция и эффект должны фиксироваться вместе. Если сохранить ключ отдельно до эффекта — можно потерять операцию; если после эффекта — повторить её. При одинаковом ключе и содержимом возвращай исторический результат команды, даже если текущее состояние объекта уже изменилось.

Определи хеширование значимых полей и области операции, правила канонизации и хранения. Серверная генерация ID допустима, если выбранный ID атомарно сохраняется и повтор возвращает его; требовать клиентский ID для всех систем не нужно.

Retention журнала должен покрывать обещанное окно повторов. После удаления записи прежняя гарантия может закончиться — это часть клиентского контракта, а не только уборка таблицы. Идемпотентность по ключу не предотвращает две логически одинаковые команды с разными ключами: иногда нужен дополнительный доменный инвариант.

## Проверки

В изолированной БД воспроизведи конкурентные чтения барьером, а не случайной задержкой. Проверь один и тот же ключ одновременно, тот же ключ с другим payload/операцией, раздельные tenant, откат в середине, конфликт версии, retry после serialization failure и финальный инвариант сохранённых строк. Успешные HTTP-статусы без ревизии состояния недостаточны.

Основы: РХД-3–4, ПКП-6–7 и примеры CQRS.
