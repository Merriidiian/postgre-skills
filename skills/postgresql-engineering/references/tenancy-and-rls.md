# Мультитенантность и RLS

## Модель доверия

Tenant определяет сервер после аутентификации и проверки членства/полномочий. Произвольный `X-Tenant-ID` не является доказательством доступа. Явная передача tenant, составные FK, SQL-фильтры и RLS дополняют друг друга.

В общей модели tenant-таблицы обычно имеют `tenant_id NOT NULL`, tenant-локальные ключи и FK. Отдельные схемы, базы или кластеры выбирай по изоляции, стоимости обслуживания и требованиям восстановления. Глобальные справочники имеют отдельную модель прав.

RLS с контекстом в пользовательском GUC страхует ошибки фильтрации доверенного приложения. Он не защищает от сервиса, способного произвольно выбрать GUC, SQL injection с такими возможностями, суперпользователя или утечки резервной копии. Пользовательские права внутри одного tenant тоже нужно проектировать отдельно.

## Роли и политики

Разделяй владельца/мигратора и runtime-роли. Приложение не должно работать как superuser, с `BYPASSRLS` или как владелец таблиц, рассчитывая только на обычный `ENABLE ROW LEVEL SECURITY`.

Пример для уже существующих таблицы `tasks`, схемы `app` и обычной роли `app_runtime`:

```sql
CREATE FUNCTION app.current_tenant() RETURNS uuid
LANGUAGE sql STABLE
AS $$
    SELECT nullif(current_setting('app.tenant_id', true), '')::uuid
$$;

ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;
ALTER TABLE tasks FORCE ROW LEVEL SECURITY;

CREATE POLICY tasks_tenant_isolation ON tasks
    TO app_runtime
    USING (tenant_id = app.current_tenant())
    WITH CHECK (tenant_id = app.current_tenant());
```

Роль должна иметь необходимые обычные GRANT на схему, функцию и разрешённые операции таблицы: RLS не выдаёт права сама. Отсутствующий или пустой tenant приводит к NULL и не разрешает строку; некорректный UUID завершится ошибкой. Не подставляй tenant по умолчанию при ошибке контекста.

- `USING` ограничивает видимые существующие строки, `WITH CHECK` — допустимое новое состояние.
- Если подходящих политик нет, при включённой RLS обычная роль получает запрет по умолчанию. Учитывай обычные привилегии и комбинацию всех действующих политик.
- Для `FOR ALL` выражение `USING` может неявно использоваться и как `WITH CHECK`; явная запись делает намерение понятнее. Отсутствие явно написанного `WITH CHECK` не всегда означает возможность чужой записи.
- Владелец обычно обходит RLS; `FORCE` подчиняет владельца политикам. Superuser и `BYPASSRLS` продолжают обходить их.
- Несколько permissive-политик объединяются через OR. Дополнительная широкая политика способна снять ожидаемое ограничение; restrictive-политики имеют другую роль и не заменяют анализ всей комбинации.
- RLS не покрывает все операции, например `TRUNCATE`. Проверки ссылочной целостности обходят видимость RLS и могут раскрывать существование ключа через ошибку. Ограничивай привилегии и внешний текст ошибки.
- Для views, `SECURITY DEFINER` и функций отдельно проверь роль исполнения, права и `search_path`. Не объявляй функцию `SECURITY DEFINER` ради обхода затруднений с политиками.

`STABLE` у функции отражает неизменность результата в рамках оператора. Это не обещание «вызов ровно один раз». Смотри фактический план под runtime-ролью.

## Tenant-контекст и пул

Все запросы одного действия выполняй через один transaction handle:

```text
tx = Begin
tx.Exec("SELECT set_config('app.tenant_id', $1, true)", verifiedTenant)
tx.Query/Exec(... с tenant-параметрами ...)
tx.Commit
```

Параметр `true` делает настройку локальной для транзакции. После COMMIT/ROLLBACK восстанавливается прежнее session-значение, если оно было. Поэтому не устанавливай tenant через долгоживущий session `SET` и проверь исходное состояние соединений. Локальная настройка не исправляет уже загрязнённый session-контекст сама по себе.

Установка через `pool.Exec`, а затем запрос через `pool.Query` не гарантирует одно соединение. Не возвращай соединение в пул между установкой контекста и использованием. При новом `BEGIN` после retry устанавливай tenant заново. Явный `BEGIN` важен также для transaction pooling.

У relay, проектора и администратора могут быть другие необходимые области доступа. Выделяй им минимальные привилегии и отдельные политики, а не универсальный обход RLS для всех работников.

## Отрицательная проверка

Проверяй под настоящей runtime-ролью; `SET ROLE` из привилегированной сессии требует проверки `current_user` и фактических атрибутов роли.

1. Без tenant-контекста нельзя получить/создать tenant-данные.
2. Tenant A не читает, не меняет и не удаляет данные B, даже если в тестовом SQL забыт фильтр.
3. Вставка/смена `tenant_id` на B отклоняется; составной FK не допускает чужой parent.
4. После COMMIT и после ROLLBACK то же физическое соединение безопасно обслуживает другого tenant; проверь последовательность A → без контекста → B.
5. Проверяются все tenant-таблицы, Inbox/Outbox и проекции, а не одна показательная таблица.
6. Новый запрос через пул и новая попытка транзакции заново устанавливают проверенный контекст.

Основы: РХД-2, РХД-4–6 и лекция о мультитенантности; семантика ролей и политик уточнена по официальной документации PostgreSQL.
